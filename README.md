# dsh-live-compact-local

**dsh-live-compact 1.1.1 的本地化分支**。核心修复直接改在源码里，不依赖 pnpm patch，
也不再跟上游发版节奏。

- 上游：`dsh-live-compact` by MerkyorLynn（MIT）
- 基线：**1.1.1**
- 本分支：**1.1.1-local.3**

> 写给上游作者和后来者：这是我们这边**验证过、正在跑**的一条路。不是要说服谁，
> 只是把实测数据和代码放出来，能参考就参考。详细来龙去脉见 `HANDOFF.md`。

## 一、我们的结论

**1.1.1 是唯一稳定基线。1.1.2 / 1.1.3 的修法在我们这台机器上都失败了，已回退。**

| 版本 | 做法 | 我们的实测结果 |
|---|---|---|
| 1.1.1 原版 | 每轮全量 `statSync` | ❌ 卡 8~19 秒 |
| **1.1.1 + 本地补丁** | 用量记账 + 快路径 | ✅ **不卡** ← 就是这套 |
| 1.1.2 | 估算快路径 + 独占模式 | ❌ 默认目录恒不生效；独占模式重启即废（#35） |
| 1.1.3 | `setImmediate` 异步化 | ❌ 更卡 + 丢输出（全局变量并发竞争） |

四组对照实验（同一 shadow 目录，13k 文件）：
**1.1.1+补丁 ✅ / 1.1.3+新补丁 ❌ / 1.1.3 原版 ❌ / 1.1.1 原版 ❌**

## 二、根因：900ms 花在哪（逐段实测，不是估算）

本机 shadow = 6,728 个文件时：

```
readdir 目录树        14 ms   便宜
+ statSync 每个文件  433 ms   要 size 才能算用量
+ readSessionKey     459 ms   逐个打开文件读头部
                              —— 而 98.9% 是 raw-，压根没有会话头
──────────────────────────
 合计                906 ms   全是同步 I/O，事件循环完全停摆
```

`finishTurn` 每轮最多 8 个 pass，每个 pass 存一次备份就再跑一遍
→ **8 × 0.9s ≈ 7 秒**，与「卡 10 秒」吻合。

荒谬点：**shadow 才 12MB、上限 256MB，一个都不用删，却每次要把近 7000 个文件全摸一遍才得出这个结论。**

事件循环停摆正好解释全部症状：HTTP 发不出响应 → 「深度求索中」散不掉、
打断请求排在后面、切会话加载不出历史。

## 三、修法（local.3）

### 五处改动

| # | 改动 | 为什么 |
|---|---|---|
| 1 | **记账集中到唯一写口** `writeShadowFile` + 删除点 | 旧版靠调用方手动上报（`raw.js` 自己调 `bumpShadowEstimate`），漏一处账就永久偏低 |
| 2 | **快路径不查目录，但也不靠"定时强制校准"兜底** | 见下节，这是最关键的一条 |
| 3 | 只在**真要删**时才逐个 `statSync` | 那时本来就要知道删谁、多大 |
| 4 | **`raw-` 跳过读会话头** | 文件名已含全部信息，归属由所在目录决定，省掉 459ms |
| 5 | 上限口径与上游一致：只算正文，`meta`/`owner`/`stats` 不计入 | 旧版本地补丁把 meta 也算进去，口径不一致 |

**删除逻辑本身一行没动**，容量管理行为完全不变（该删的照删、受保护文件不动、活会话不动）。

### 关键：为什么不用「每 60 秒强制校准」

我们上一版（local.2）就是加了这个护栏。实测发现它**等于定时制造悬崖**：

| 场景 | local.2（60 秒护栏） | local.3 |
|---|---|---|
| 一轮 8 个 pass | 8 × 0.9s ≈ **7.2s（卡顿复现）** | **0.05ms** |
| 连续跑 5 分钟 | 5 次 × 0.9s ≈ **4.5s 卡顿** | 全程 **1.1ms** |
| 卡顿形态 | 间歇性、越聊越卡 | 无 |

一轮对话超过 60 秒是常态 → 每过一个 60 秒就吃一次 900ms 的同步全量扫描。
**护栏本意是兜底，实际是把"偶发卡顿"变成了"定时卡顿"。**

local.3 换成**点数校验**：

- 热路径先做一次 `readdir` 数文件（14ms，不 stat、不开文件）
- 新增必然 +1、删除必然 −N → **任何漏记都会被点数抓住**
- 对得上就放行；对不上立刻全量重算
- 再加两个上限保护：用量过 cap 的 60%（接近水线）或超过 30 秒没校验，才主动点数

**不再定时强制校准 → 悬崖消失，同时保留"漏记能被发现"的兜底。**

## 四、实测数据

### 真机 shadow（13,480 个条目）

```
首次全量校准      484ms        每进程一次
热路径 50 次      max 0.09ms / avg 0.006ms
一轮 8 个 pass    0.05ms       （旧版 ≈ 7200ms）
模拟 300 次调用   1.1ms        （旧版含 5 次悬崖 ≈ 4500ms+）
真实目录文件数    13480 → 13480   一个没动
```

### 回归测试 20 项全过

方法：建 6500 个文件的仿真 shadow，**以磁盘实测为唯一真值**（不信任函数自己的返回值）。

覆盖：用量与磁盘一致 / 写入后不退化 / **外部写入被抓** / **外部删除被抓** /
真触线删除且账目归零 / 活会话文件保住 / 删后热路径立即恢复 /
meta 不计入 cap / 换目录账不串 / oversize 照写 / 连续 20 次无悬崖。

## 五、给上游的三条实测反馈

写在这里，因为 Issue 里已经讨论过，这是我们这边的复现结论：

1. **「只对专用目录启用估算」这个默认值，让绝大多数用户吃不到修复。**
   我们本机 `DSH_HOME` 下的默认根就是实际使用的目录，`dedicatedRoot()` 里
   `return normal !== root` 恒为 false。装 1.1.2 之后卡顿一点没变。
   —— 这不是"需要配置"，是"默认情况下这个修法不存在"。

2. **独占模式的 per-process 随机 token 让方案不可用。**
   `owner` 文件一旦写过，只有写它的那个进程能对上号；那个进程一退出，
   这个根就再也用不了独占模式（#35）。第一次启动能进（4~6ms），重启后永久退化。

3. **`setImmediate` 治不了同步 I/O。**
   它只改"什么时候开始"，不改"开始后阻塞多久"——`captureOne` 里面还是同步的。
   而且引入模块级全局变量在异步回调间交错覆盖 → 锁验证失败 → 清缓存 + 丢输出。

## 六、怎么用

### 方式 A：只打最小补丁（推荐，改 2 个文件）

如果你想留在官方 1.1.1 上，只拿我们的 `shadow.js` 快路径部分：

1. 用本仓库的 `src/prebuilt/shadow.js` 替换官方的同名文件
2. 用本仓库的 `src/prebuilt/raw.js` 替换（去掉旧的 `bumpShadowEstimate` 调用）
3. `node --check` 过一遍，重启

`shadow.js` 里的改动都带 `【本地补丁】` 注释，方便对照和裁剪。

### 方式 B：整包用本分支

```bash
# 1. 放到 local-plugins（你 profile 下的目录）
# 2. profile 的 package.json：
#    "dependencies": { "dsh-live-compact-local": "file:./local-plugins/dsh-live-compact-local" }
#    "dsh": { "profile": { "bundles": [ ..., "dsh-live-compact-local" ] } }
#    ⚠️ 两处都要有，少一处插件不加载
# 3. pnpm install
# 4. 重启
```

`cordis.patch.yml` 里已经把 `compaction-basic` 设为 `disabled: true`（腾出 `ctx.compaction` 位），
并把两处 `name` 改成了 `dsh-live-compact-local`。

### ⚠️ 部署坑（我们踩过）

- **`node_modules` 里那份是硬链接，不是符号链接。** 改源码后复制到 `local-plugins`，
  `node_modules` 会同时变——**但宿主进程启动时已加载旧代码，必须重载或重启才生效**。
- **验证脚本要 import `node_modules` 那份**，不是源码那份。否则你测的是旧代码（踩过，白测一轮）。
- 改 `.js` → 热重载（`plugin_manager` 关→开）；改 `package.json` / `cordis.patch.yml` → 冷重启。

## 七、已知限制（诚实交代）

| 项 | 状态 | 说明 |
|---|---|---|
| **同步 I/O 改异步** | ⏸ 未做 | 根本解，但 `rotateShadow` 要变 async，调用链全改。估算已干掉热路径，收益边际 |
| **点数校验是每次 14ms** | ⚠️ 取舍 | 相比旧版每次 900ms 便宜 60 倍；只在接近水线/超 30 秒时才真正点数 |
| **`MAP_LIMIT = 800`** | ⚠️ 经验值 | `rawSeen`/`callIndex` 的淘汰上限，没压测过最佳值 |
| **没做并发安全** | ⚠️ | 我们只用单进程场景；多进程共享同一 shadow 根的语义没有验证 |
